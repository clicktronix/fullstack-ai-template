Auth Boundary Chain

src/proxy.ts is explicitly not the authorization boundary — it only refreshes sessions, redirects, and applies CSP/security headers. Every real authorization check happens again, server-side, at the DAL/inbound layer.

  • server-only markers: every secret/cookie/service-role-touching shared module has import 'server-only' — adapters/supabase/{admin,server,server-query}.ts, infrastructure/auth/*, infrastructure/api/*, infrastructure/cache/tags.ts, infrastructure/env/server.ts, infrastructure/logging/server-logger.ts, outbound *.operations.ts (T1).
  • Framework-excluded exceptions: app/auth/callback/route.ts, app/(protected)/layout.tsx, and server-actions/auth.ts ('use server') touch cookies()/headers() without the server-only package — not violations, Next.js itself excludes route/layout/server-action files from client bundles (T1).
  • No Client Component ever imports a server-only module — the only client-side imports of @/adapters/* are the two documented anon-key browser exceptions in ui/server-state (see Layers).
  • Secrets are never NEXT_PUBLIC_*: infrastructure/env/server.ts validates SUPABASE_SECRET_KEY, SUPABASE_SERVICE_ROLE_KEY, AI_SUGGESTIONS_API_KEY, EXAMPLE_WEBHOOK_SECRET — none prefixed NEXT_PUBLIC_. infrastructure/env/public.ts only exposes NEXT_PUBLIC_* vars (Supabase URL/anon key, site URL, Sentry DSN).
  • DTO out: outbound repositories select an explicit column list matching the domain schema (e.g. WORK_ITEM_SELECT = Object.keys(WorkItemSchema.entries).join(', ')) and pass every result through parse(Schema, data) — raw Postgrest rows are never returned to the UI (T1).

Error-Capture Map — "Once-Only" Rule

Four new boundaries (added in this branch) each own exactly one slice of the error surface. No error is meant to reach Sentry twice.

Redact-before-send, everywhere: redactSentryEvent (infrastructure/sentry/redact.ts, built on log-redaction.ts) is wired as beforeSend in all three Sentry entry points — sentry.server.config.ts, sentry.edge.config.ts, and (added in this branch) instrumentation-client.ts — so browser-originated captures (e.g. QueryCache.onError, which runs client-side) are redacted too, not just server-side ones.

Render boundaries vs. capture boundaries — not the same thing

ui/components/ErrorBoundary and ApiErrorBoundary are React render-error boundaries (via react-error-boundary) that classify ApiError subclasses (NetworkError, UnauthorizedError, ForbiddenError, NotFoundError, ServerError) to show a fallback UI. They only render what throwOnError in query-client.ts decides to re-throw (5xx/network only) — they do not call Sentry.captureException themselves; that already happened once at the boundary that first caught the error, per the table above.
